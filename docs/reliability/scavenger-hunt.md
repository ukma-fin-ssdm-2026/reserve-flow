## R-01. Бронювання без запису аудиту, а клієнт отримує `500`

**Категорія:** A (обробка помилок), D (непередбачена поведінка там, де потрібна чітка помилка)

```python
# routes/bookings.py — create_booking
booking = booking_engine.create_booking(...)   # усередині session.commit() — бронювання вже в БД
audit = AuditLog(...)
session.add(audit)
session.commit()                               # другий, окремий коміт
```

**Чому небезпечно:** сервіс обіцяє «усе в одній транзакції», але аудит (FR-013) пишеться другою транзакцією. Якщо другий коміт падає (обрив з'єднання, обмеження БД), перший уже не відкотити.

**Потенційний вплив:** клієнт бачить `500` і пробує ще раз — отримує `409 SLOT_UNAVAILABLE`, бо слот зайняв він сам; бронювання існує, але в журналі дій його немає.

| Поле | Опис |
|---|---|
| Несправність | Два коміти замість одного: `AuditLog` додається після `session.commit()` у сервісі |
| Помилка | У БД є `Booking` без відповідного `AuditLog`; відповідь ще не відправлена |
| Відмова | Клієнт отримує `500`, повтор — `409`; адміністратор не бачить створення в журналі |
| Критичність | **висока** — запис даних, порушено FR-013 і очікування клієнта |

**Як перевірено (відтворено):** підмінили `AuditLog` на функцію, що кидає виняток → `POST /bookings` повернув `500`, кількість бронювань 1 → 2; повторний запит → `409 SLOT_UNAVAILABLE`.

## R-02. Бронювання слота в минулому

**Категорія:** C (відсутні граничні перевірки)

```python
# services/bookings.py — create_booking
slot = lock_slot(session, slot_id)
if not slot:
    raise SlotNotFound()
if not slot.is_available:          # перевіряється лише закриття постачальником,
    raise SlotUnavailable(...)     # але не те, що слот уже почався чи минув
```

**Чому небезпечно:** ні сервіс, ні `GET /slots` не порівнюють `start_time` з поточним часом; пошук теж повертає минулі слоти.

**Потенційний вплив:** у системі з'являються «активні» бронювання на минулий час: вони блокують перевірку перетину (FR-016), потрапляють постачальнику на підтвердження, а нагадування для них ставиться в минуле (див. R-06).

| Поле | Опис |
|---|---|
| Несправність | Немає перевірки `slot.start_time > now` у `create_booking` і в пошуку |
| Помилка | Створено `Booking(Pending)` на слот, що вже завершився |
| Відмова | API відповідає `201` на неможливу дію замість чіткої помилки; користувач думає, що бронювання дійсне |
| Критичність | **висока** — неправильна відповідь гірша за відсутність: це має бути швидка відмова (`409`/`422`) |

**Як перевірено (відтворено):** додали слот на 01.01.2020 → `POST /bookings` повернув `201`.

## R-03. Блокувальний ввід-вивід в асинхронних обробниках

**Категорія:** E (блокувальний ввід-вивід в асинхронному коді)

```python
@router.get("")
async def get_bookings(..., session: Annotated[Session, Depends(get_session)], ...):
    all_bookings = session.exec(stmt).all()   # синхронний драйвер psycopg усередині async def
```

**Чому небезпечно:** FastAPI запускає `async def` прямо в циклі подій, а синхронні `session.exec` / `session.get` блокують його на весь час запиту до БД. Звичайні `def`-обробники FastAPI виконує в пулі потоків — у них цієї проблеми немає (так зроблено `create_booking`). Асинхронні: `get_bookings`, `get_booking`, `update_booking`, `search_slots`, `patch_slot`.

**Потенційний вплив:** один повільний запит до БД зупиняє обробку **всіх** запитів воркера, зокрема перевірку здоров'я; під навантаженням PERF-001 (≤ 5 с при 10 користувачах) не виконується.

| Поле | Опис |
|---|---|
| Несправність | `async def` + синхронна `Session` |
| Помилка | Цикл подій заблоковано на час запиту до БД; інші запити стоять у черзі |
| Відмова | Затримки й тайм-аути в усіх користувачів одночасно, не лише в того, чий запит повільний |
| Критичність | **висока** — збій однієї операції поширюється на весь сервіс |

## R-04. Немає тайм-аутів на роботу з БД

**Категорія:** B (виклики БД без тайм-аутів), E (довгі операції в обробнику)

```python
# db.py
return create_engine(url, pool_pre_ping=True, **kwargs)   # без connect_timeout / statement_timeout

# services/rooms.py — lock_slot
select(TimeSlot).where(TimeSlot.id == slot_id).with_for_update()   # без NOWAIT / lock_timeout
```

**Чому небезпечно:** не задано ні тайм-аут з'єднання, ні тайм-аут запиту, ні тайм-аут очікування блокування. `SELECT … FOR UPDATE` чекає, доки інша транзакція не відпустить рядок, — скільки завгодно.

**Потенційний вплив:** якщо транзакція, що тримає слот, зависла, усі наступні бронювання цього слота висять без відповіді; при недоступній БД запит чекає на мережевий тайм-аут ОС (хвилини). Разом з R-03 це зупиняє весь сервіс.

| Поле | Опис |
|---|---|
| Несправність | Відсутні `connect_timeout`, `statement_timeout`, `lock_timeout` |
| Помилка | Запит чекає на з'єднання або блокування без обмеження в часі |
| Відмова | Користувач не отримує жодної відповіді (зависання), замість швидкої `503`/`409` |
| Критичність | **висока** — немає жодної межі для найчастішої зовнішньої залежності |

## R-05. Перевірка здоров'я не перевіряє залежності

**Категорія:** D (мовчазний збій)

```python
@app.get("/api/v1/health", tags=["System"])
def health_check():
    return {"status": "healthy"}
```

**Чому небезпечно:** відповідь не залежить від стану БД. До того ж engine створюється ліниво (`db.get_engine`), тож навіть відсутній `POSTGRES_PASSWORD` проявиться `KeyError` лише на першому запиті з БД, а `health` і далі «здоровий».

**Потенційний вплив:** хостинг / балансувальник вважає сервіс робочим і шле на нього трафік, хоча всі запити з даними падають з `500`.

| Поле | Опис |
|---|---|
| Несправність | `health_check` повертає константу |
| Помилка | Зовнішні системи мають хибне уявлення про стан сервісу |
| Відмова | Перезапуску чи перемикання немає; користувачі отримують `500`, моніторинг показує «все добре» |
| Критичність | **середня** — сама не ламає дані, але приховує інші відмови |

**Як перевірено (відтворено):** зламали залежність `get_session` → `GET /api/v1/health` однаково `200 {"status": "healthy"}`.

## R-07. `GET /bookings` читає всю таблицю і робить N+1 запитів

**Категорія:** E (довгі операції в обробнику запиту)

```python
all_bookings = session.exec(stmt).all()                                     # усі бронювання системи
filtered = [b for b in all_bookings if _can_view(session, current_user, b)]  # +2 запити на кожне
items = [_to_out(b) for b in filtered]
return paginate(items, params)                                              # сторінка — уже в пам'яті
```

**Чому небезпечно:** фільтр доступу й пагінація виконуються в Python, а не в SQL; для постачальника `_can_view` робить `session.get(TimeSlot)` і `session.get(Room)` на кожне бронювання. Час відповіді росте лінійно з кількістю всіх бронювань, а не з розміром сторінки (`limit ≤ 100` нічого не обмежує). Те саме в `search_slots`: усі доступні слоти читаються й фільтруються в пам'яті.

**Потенційний вплив:** з ростом даних список бронювань і пошук сповільнюються до тайм-аутів; разом з R-03 блокують інші запити.

| Поле | Опис |
|---|---|
| Несправність | Вибірка без `WHERE` за власником / `LIMIT` / `JOIN` |
| Помилка | Тисячі рядків і запитів на один HTTP-запит |
| Відмова | Повільна сторінка «Мої бронювання», тайм-аут при навантаженні |
| Критичність | **середня** — на seed-даних непомітно, проявиться з ростом БД |

## R-08. Гонка під час зміни статусу бронювання

**Категорія:** D (непередбачена поведінка)

```python
booking = _get_booking_or_404(session, booking_id)            # звичайне читання, без FOR UPDATE
if booking.status.value not in _ALLOWED_FROM[booking_in.status]:
    raise AppError(...)                                        # перевірка на застарілих даних
booking.status = booking_in.status
session.commit()
```

**Чому небезпечно:** на відміну від `create_booking`, тут немає блокування рядка. Постачальник підтверджує, а клієнт одночасно скасовує: обидва запити читають `Pending`, обидва проходять перевірку переходу, перемагає останній коміт.

**Потенційний вплив:** обидва отримують `200`; у журналі два записи (`CONFIRMED` і `CANCELLED`), а фінальний стан залежить від того, хто встиг пізніше — машина станів (D-03) порушена.

| Поле | Опис |
|---|---|
| Несправність | Перевірка «з якого статусу» без блокування рядка |
| Помилка | Перехід застосовано до вже зміненого бронювання (lost update) |
| Відмова | Одна зі сторін бачить успіх, якого насправді немає; журнал суперечить стану |
| Критичність | **середня** — потребує одночасних дій, але зачіпає ключовий сценарій |

## R-09. `X-Correlation-ID` від клієнта не перевіряється

**Категорія:** C (неперевірений зовнішній вхід)

correlation_id = request.headers.get("X-Correlation-ID", str(uuid.uuid4()))

**Потенційний вплив:** клієнт може підробити або повторити чужий ID і заплутати пошук у логах; дуже довгі значення роздувають логи.

| Відмова | Підтримка не може знайти запит за ID з помилки; кореляція логів ненадійна |
| Критичність | низька |

## R-10. Строк дії токена з оточення не перевіряється

**Категорія:** C (відсутня перевірка типів / граничні перевірки)

```python
def access_token_ttl() -> timedelta:
    return timedelta(minutes=int(os.getenv("ACCESS_TOKEN_EXPIRE_MINUTES", "30")))
```

**Чому небезпечно:** значення читається під час кожного входу, а не при старті. `"30m"` → `ValueError`; `0` або від'ємне число → токен прострочений одразу після видачі.

**Потенційний вплив:** після помилки в конфігурації сервіс стартує «здоровим», але ніхто не може увійти: `500` на `POST /auth/token` або `401` на кожен запит з щойно виданим токеном.

| Поле | Опис |
|---|---|
| Несправність | `int(os.getenv(...))` без обробки й без меж (ADR-003: 15–30 хв) |
| Помилка | `ValueError` під час видачі токена або `exp ≤ iat` |
| Відмова | Вхід у систему неможливий; причина видна лише в логах |
| Критичність | низька — залежить від помилки конфігурації, але блокує всіх |

## R-11. Занадто широке перехоплення при старті

**Категорія:** A (занадто широке перехоплення)

```python
try:
    export_openapi(app)
except ImportError:
    logging.warning("Модуль export_openapi не знайдено. Експорт пропущено.")
except Exception as e:
    logging.error(f"Помилка експорту OpenAPI: {e}")
```

**Чому небезпечно:** будь-яка помилка (зламана схема, немає прав на запис) перетворюється на один рядок у лозі без traceback, і застосунок продовжує працювати.

**Потенційний вплив:** на GitHub Pages і в `docs/api/` лишається застаріла специфікація; причину важко знайти без стеку виклику.

| Поле | Опис |
|---|---|
| Несправність | `except Exception` + `logging.error` замість `logging.exception` |
| Помилка | Специфікація не оновлена, стек виклику втрачено |
| Відмова | Клієнти API читають неактуальну документацію |
| Критичність | низька — експорт не критичний для роботи API, тому безпечна відмова тут доречна, але бракує повного логування |
