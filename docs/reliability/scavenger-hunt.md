## 1. Блокувальний I/O в асинхронних обробниках — **E**

> **Статус (10.11):** ✅ **Виправлено** в #437 (коміт `6d097ea`): усі обробники з синхронною `Session` тепер `def` — FastAPI виконує їх у пулі потоків. Тест: `tests/test_no_blocking_in_async.py`.

```python
# routes/bookings.py (так само search_slots, patch_slot, get_room)
async def get_bookings(..., session: Annotated[Session, Depends(get_session)], ...):
    all_bookings = session.exec(stmt).all()          # синхронний виклик psycopg
    filtered = [b for b in all_bookings if _can_view(session, current_user, b)]
```

**Чому небезпечно.** FastAPI виконує `async def` прямо в event loop. `Session.exec()` — блокувальний
мережевий виклик до PostgreSQL. Поки він чекає на БД, увесь воркер uvicorn не обробляє жодного
іншого запиту. На Render у нас один процес, тобто один повільний запит «заморожує» весь API.
Звичайний `def` (як у `create_booking`) FastAPI сам виносить у пул потоків — там проблеми немає.

**Потенційний вплив.** Різке зростання затримок для всіх користувачів; healthcheck Render не
відповідає вчасно → сервіс перезапускається посеред роботи. Ефект підсилюється знахідками №2, №3, №5.

**Як виправити.** Замінити `async def` на `def` у всіх обробниках, що працюють із синхронною `Session`
(або перейти на `AsyncSession`).

## 2. Немає тайм-аутів до БД — **B / E**

> **Статус (10.11):** ✅ **Виправлено** в #437 (коміт `a71fed2`): `db.py:33-47` — `connect_timeout` 5 с, `pool_timeout` 5 с, `statement_timeout` 5 с; перевищення → `503 SERVICE_UNAVAILABLE` з `Retry-After`. Тест: `tests/test_db_timeouts.py`.

```python
# db.py
return create_engine(url, pool_pre_ping=True, **kwargs)
```

**Чому небезпечно.** Не задано ні `connect_timeout` (скільки чекати TCP-з'єднання), ні
`statement_timeout` (скільки може виконуватися запит), а `pool_timeout` лишився стандартним (30 с).
Якщо БД недоступна або «зависла», запит чекає на рівні ОС хвилинами. Це саме той випадок із §3.2:
виклик, нічим не обмежений у часі.

**Потенційний вплив.** Вичерпання пулу з'єднань (5 + 10 overflow) → нові запити стоять у черзі →
каскадна відмова всього API, хоча проблема лише в одному повільному запиті.

**Як виправити.**
```python
create_engine(
    url, pool_pre_ping=True, pool_timeout=5,
    connect_args={"connect_timeout": 5, "options": "-c statement_timeout=5000 -c lock_timeout=3000"},
)
```

## 3. Блокування рядка без тайм-ауту — **E**

> **Статус (10.11):** ✅ **Виправлено** в #437 (коміт `a71fed2`): `lock_timeout` 3 с для кожного з'єднання (`db.py:47`). `with_for_update()` у `services/rooms.py:17` лишився, але чекає на блокування не довше 3 с → `503`. Тест: `tests/test_db_timeouts.py`.

```python
# services/rooms.py
statement = select(TimeSlot).where(TimeSlot.id == slot_id).with_for_update()
```

**Чому небезпечно.** Паралельний запит на той самий слот чекає, поки перша транзакція зробить
`COMMIT`. Якщо перша транзакція «застрягла» (повільна мережа, процес завис), друга чекає необмежено
довго — тайм-ауту на очікування блокування немає.

**Потенційний вплив.** Під час «гарячого» запису на популярну аудиторію запити накопичуються,
тримаючи з'єднання з пулу, — та сама каскадна відмова, що в №2.

**Як виправити.** `lock_timeout` на рівні сесії (див. №2) або `with_for_update(nowait=True)` і
перетворення `OperationalError` на `409 SLOT_UNAVAILABLE`.

## 4. Неатомарне створення бронювання й аудиту — **A / D**

> **Статус (10.11):** ✅ **Виправлено** в #437 (коміт `a6a42db`): `AuditLog` записується в тій самій транзакції, що й бронювання та нагадування (`services/bookings.py:105-113`). Тест: `tests/test_booking_atomic_audit.py`.

```python
# routes/bookings.py
booking = booking_engine.create_booking(...)   # всередині вже session.commit()
audit = AuditLog(...)
session.add(audit)
session.commit()                               # окрема, друга транзакція
```

**Чому небезпечно.** Бронювання вже збережене, коли ми пишемо аудит. Якщо другий `commit()` впаде
(обрив з'єднання, тайм-аут), клієнт отримає `500`, хоча бронювання створено. Повтор запиту дасть
`409 SLOT_UNAVAILABLE` — на власне бронювання. Аудит (FR-013) при цьому мовчки втрачено.

**Потенційний вплив.** Розбіжність даних (бронювання без запису в журналі), заплутаний UX,
неможливість довести, хто що робив.

**Відтворено.** Тимчасовий тест через `TestClient` на seed-даних: `AuditLog` у `routes/bookings.py`
підмінено функцією, що кидає виняток → `POST /api/v1/bookings` = `500`, кількість бронювань у БД
1 → 2; повтор того самого запиту → `409 SLOT_UNAVAILABLE`.

**Як виправити.** Додавати `AuditLog` у тій самій транзакції всередині `services/bookings.create_booking`
перед єдиним `commit()`.

## 5. Пагінація в пам'яті і N+1 — **E**

> **Статус (12.11):** ✅ **Виправлено** в #467: `routes/bookings.py::_visible_bookings` будує фільтр доступу в SQL (клієнт — `client_id`, постачальник — `JOIN time_slots, rooms` за `provider_id`, адміністратор — без фільтра); `get_bookings` рахує `total` через `COUNT` і вибирає сторінку `ORDER BY created_at, id … OFFSET … LIMIT`. На сторінку — 3 SQL-запити незалежно від розміру БД (було для постачальника 28 на 12 бронюваннях і 108 на 52). `_can_view` лишився для `GET`/`PATCH /bookings/{id}`. Тест: `tests/reliability/test_bookings_list_query.py`.

```python
all_bookings = session.exec(select(Booking)).all()                         # уся таблиця
filtered = [b for b in all_bookings if _can_view(session, current_user, b)]  # +2 SELECT на кожне
return paginate(items, params)                                             # limit/offset у Python
```

Те саме в `search_slots`: усі слоти + усі `slot_id` активних бронювань, фільтр за датою/часом у Python.

**Чому небезпечно.** Час відповіді росте лінійно з розміром БД, а не з розміром сторінки.
Для постачальника кожне бронювання — ще 2 запити (`TimeSlot`, `Room`). 10 000 бронювань ≈ 20 000 запитів
на один `GET`.

**Потенційний вплив.** Тайм-аути, витрата пам'яті, блокування event loop (разом із №1). Легкий
спосіб випадково «покласти» сервер звичайним запитом списку.

**Як виправити.** Фільтр доступу через `JOIN` у SQL, `LIMIT/OFFSET` і `COUNT(*)` на боці БД.

## 6. Гонка при зміні статусу — **D**

> **Статус (10.11):** ✅ **Виправлено** в #437 (коміт `c2a4ada`): умовний `UPDATE … WHERE status = <перевірений>` і перевірка `rowcount` (`routes/bookings.py:279-282`) → `409` замість хибного `200`. Тест: `tests/test_booking_status_race.py`.

```python
booking = _get_booking_or_404(session, booking_id)        # звичайний SELECT, без блокування
if booking.status.value not in _ALLOWED_FROM[booking_in.status]: ...
booking.status = booking_in.status
session.commit()
```

**Чому небезпечно.** Два одночасні запити (постачальник підтверджує, клієнт скасовує) обидва
читають `Pending`, обидва проходять перевірку, і перемагає той, хто закомітив останнім.
Помилки немає — стан просто «перезаписується» (lost update).

**Потенційний вплив.** Обидві сторони отримують `200`, але зміна однієї з них фактично не відбулася:
наприклад, клієнт бачить «скасовано», а бронювання лишилося `Confirmed`. У журналі аудиту два записи
(`BOOKING_CONFIRMED` і `BOOKING_CANCELLED`), що суперечать фінальному стану. Подвійного бронювання
при цьому не буде: слот з активним бронюванням виключається і з `GET /slots` (`booked_ids`), і з
`create_booking` (перевірка `taken`), навіть якщо `is_available` уже `True`.

**Як виправити.** `SELECT ... FOR UPDATE` для бронювання або умовний `UPDATE ... WHERE status = :old`
з перевіркою кількості змінених рядків.

## 7. Healthcheck не перевіряє залежності — **B / D**

> **Статус (12.11):** ✅ **Виправлено** в #458 (бонус): `/api/v1/health` виконує `SELECT 1` (тайм-аути з `db.py`: з'єднання, пул і запит — до 5 с). БД відповіла → `200 {"status": "healthy", "db": "ok"}`; будь-яка помилка SQLAlchemy → `503 {"status": "unhealthy", "db": "unavailable"}` без внутрішніх деталей, у лозі — попередження з типом помилки. Мертвий `routes/health.py` тепер підключено (з `main.py` маршрут прибрано); `operationId` не змінився, тож інструмент MCP `check_health` працює як раніше. @app.get("/api/v1/health", tags=["System"])
```python
def health_check():

```

**Чому небезпечно.** `render.yaml` використовує `/api/v1/health` як `healthCheckPath`. Ендпоінт
відповідає «healthy», навіть коли PostgreSQL недоступна. Окремо: `routes/health.py` (з перевіркою

**Потенційний вплив.** Платформа вважає сервіс здоровим, а всі бізнес-запити повертають `500` —
мовчазний збій, про який ніхто не дізнається.

**Відтворено.** Тимчасовий тест через `TestClient` на seed-даних: залежність `get_session` підмінено
функцією, що кидає виняток → `GET /api/v1/health` = `200 {"status": "healthy"}`, а
`GET /api/v1/bookings` у той самий момент = `500`.

**Як виправити.** Окремий readiness-ендпоінт із `SELECT 1` (з коротким тайм-аутом), що повертає
`503`, якщо БД недоступна; підключити або видалити мертвий `routes/health.py`.

## 8. Конфігурація перевіряється лише під час запиту — **C / D**

> **Статус (11.11):** ✅ **Виправлено** в #469: `config_check.validate_config()` на старті (`main.lifespan`) перевіряє `JWT_SECRET` (≥ 32 символи), `ACCESS_TOKEN_EXPIRE_MINUTES` (ціле, 5–1440) і наявність `DATABASE_URL` або `POSTGRES_PASSWORD`. Порушення → `CRITICAL` у лозі з назвами змінних (без значень) і сервер не стартує — швидка відмова. Тест: `tests/reliability/test_config_validation.py`.

```python
# db.py
password = quote_plus(os.environ["POSTGRES_PASSWORD"])   # KeyError — на першому запиті
# security.py
return timedelta(minutes=int(os.getenv("ACCESS_TOKEN_EXPIRE_MINUTES", "30")))  # "abc" → ValueError
secret = os.getenv("JWT_SECRET", "")
if len(secret) < MIN_SECRET_LENGTH:
    raise RuntimeError(...)                               # теж лише на запиті
```

**Чому небезпечно.** Сервер успішно стартує й проходить healthcheck (№7) без пароля БД чи
`JWT_SECRET`, а потім кожен запит падає з `500`. `ACCESS_TOKEN_EXPIRE_MINUTES` не має меж:
`0` або від'ємне значення дає токени, що вже прострочені; `"30m"` — `500` на кожному логіні.

**Потенційний вплив.** Деплой «зелений», а продакшн не працює. Помилку конфігурації видно
лише в логах, не на етапі запуску.

**Як виправити.** Валідувати всі змінні в `lifespan` (fail fast) і завершувати процес із чітким
повідомленням; для TTL — перевірка діапазону (наприклад, 5–60 хв).

## 9. Немає граничної перевірки часу слота — **C**

> **Статус (10.11):** ⚠️ **Розділено на дві знахідки.** **№9a** — бронювання слота, що вже почався: ❌ відкрито, план — #454. **№9b** — нагадування в минулому: ✅ виправлено в #443 (`create_booking` викликає `compute_reminder_time`, `services/bookings.py:94`; для слота, що вже почався, нагадування не створюється; тест `tests/test_booking_reminder_time.py`), уперше зафіксовано в #421.

```python
# services/bookings.py
slot = lock_slot(session, slot_id)
if not slot.is_available: ...
# перевірки slot.start_time > now немає
session.add(Notification(booking_id=booking.id, scheduled_time=slot.start_time - REMINDER_LEAD))
```

**Чому небезпечно.** Клієнт може забронювати слот, який уже почався або минув. Нагадування для
слота, що стартує менш ніж за 24 год, планується в минулому. Готова функція
`notifications.compute_reminder_time()` (яка це враховує) не використовується. Також `if not slot:`
— мертвий код, бо `lock_slot` уже кидає `SlotNotFound`.

**Потенційний вплив.** «Сміттєві» бронювання в минулому, постачальник отримує запити, які неможливо
виконати; планувальник нагадувань може масово надіслати прострочені повідомлення.

**Відтворено.** Тимчасовий тест через `TestClient` на seed-даних: доданий слот на 01.01.2020 →
`POST /api/v1/bookings` = `201 Created`.

**Як виправити.** Перевіряти `slot.start_time > now` (→ `409`), використати `compute_reminder_time`.

## 10. Файлові операції на старті без резервного шляху — **A / B / D**

> **Статус (10.11):** ❌ **Відкрито**: `main.py:35` — `except Exception as e: logging.error(...)` без стеку.

```python
# main.py
try:
    export_openapi(app)          # пише docs/api/*.json|yaml у каталог репозиторію
except ImportError:
    logging.warning(...)
except Exception as e:
    logging.error(f"Помилка експорту OpenAPI: {e}")   # без traceback
```

**Чому небезпечно.** На кожному старті продакшн-сервер пише файли у свій кодовий каталог. На
read-only файловій системі (контейнер, деякі PaaS) це падає, а помилка ховається широким
`except Exception` і логується без стеку. Окремо: якщо `yaml` не встановлено, `ImportError`
маскується як «модуль не знайдено».

**Потенційний вплив.** Неактуальна документація API без жодного сигналу; ускладнена діагностика.
Також зайвий запис на диск при кожному холодному старті.

**Як виправити.** Експортувати схему лише в CI / за прапорцем `EXPORT_OPENAPI=1`; логувати через
`logging.exception`.

## 11. Неперевірений заголовок `X-Correlation-ID` — **C / B**

> **Статус (12.11):** ✅ **Виправлено** в #468: `main.py::safe_correlation_id` приймає лише `[A-Za-z0-9-]{1,64}` (UUID підходить), інакше — новий UUID і попередження в лозі без «сирого» значення. Безпечна відмова: запит не відхиляється. Тест: `tests/reliability/test_correlation_id.py`.

```python
correlation_id = request.headers.get("X-Correlation-ID", str(uuid.uuid4()))
request.state.correlation_id = correlation_id
response.headers["X-Correlation-ID"] = correlation_id
```

**Чому небезпечно.** Значення від клієнта без перевірки формату й довжини потрапляє в логи й у
тіло помилки. Можна підробити чужий ID (сплутати розслідування), надіслати дуже довгий рядок
або символи, що ламають формат логів (log injection).

**Потенційний вплив.** Ненадійна трасованість інцидентів — саме тоді, коли вона найпотрібніша.

**Як виправити.** Приймати лише валідний UUID (або `^[A-Za-z0-9-]{1,64}$`), інакше генерувати новий.

## 12. Занадто широке перехоплення — **A**

> **Статус (10.11):** ❌ **Відкрито**: тепер `services/bookings.py:119`.

```python
# services/bookings.py
except BaseException:
    session.rollback()
    raise
```

**Чому небезпечно.** `BaseException` охоплює `KeyboardInterrupt`, `SystemExit`,
`asyncio.CancelledError`. Під час завершення процесу `rollback()` виконує мережевий виклик до БД
(без тайм-ауту, №2) і може затримати або заблокувати graceful shutdown.

**Потенційний вплив.** Довге завершення воркера під час деплою, «підвислі» транзакції.

**Як виправити.** `except Exception:` (або контекстний менеджер `with session.begin():`).

## 13. Слабка валідація текстових полів — **C**

> **Статус (10.11):** ❌ **Відкрито, частково**: у `purpose` вже є `max_length=200`, але немає обрізання пробілів; `reason` без `max_length` (`schemas/bookings.py:28-52`). План — #455.

```python
purpose: str = Field(..., min_length=3, max_length=200)   # "   " проходить
reason: str | None = Field(None, ...)                     # без max_length
```

**Чому небезпечно.** `purpose` з трьох пробілів проходить валідацію. `reason` не має обмеження
довжини і записується одразу в `bookings.rejection_reason` та `audit_log.details`.

**Потенційний вплив.** Порожні за змістом дані; запит із мегабайтним `reason` роздуває БД і логи
або падає з `500` на обмеженні колонки замість зрозумілої `422`.

**Як виправити.** `str_strip_whitespace=True` у `model_config`, `max_length=500` для `reason`.

## 14. Невідомі HTTP-коди маркуються як `INTERNAL_ERROR` — **A**

> **Статус (10.11):** ❌ **Відкрито**: `errors.py:183-192`.

```python
code, default_message = _DEFAULT_ERRORS.get(
    exc.status_code, (ErrorCode.INTERNAL_ERROR, "Помилка обробки запиту")
)
```

**Чому небезпечно.** Будь-який `HTTPException` з кодом поза 401/403/404/405 (наприклад, 400, 409,
413 від Starlette) отримує `code = INTERNAL_ERROR`, хоча статус 4xx.

**Потенційний вплив.** Клієнт і моніторинг сприймають помилки клієнта як збої сервера: хибні
алерти, неправильна логіка повторів (retry на запит, який ніколи не вдасться).

**Як виправити.** Для 4xx за замовчуванням використовувати окремий код (напр. `BAD_REQUEST`),
`INTERNAL_ERROR` — лише для 5xx.

## Етап 2. Класифікація: несправність → помилка → відмова

Більшість знахідок — **латентні несправності** (§1.4): дефект у коді є, але до відмови він доходить
лише за певних умов (навантаження, недоступна БД, паралельні запити). Тому стовпець «Відмова» описує,
що побачить користувач або інша система, **коли ланцюг замкнеться**. Умову, яка його замикає,
наведено в стовпці «Тригер».

Три ланцюги вже замкнено тимчасовими тестами через `TestClient` на seed-даних (див. «Відтворено» в описі знахідок): **№4**, **№7**, **№9** — це вже не гіпотеза, а відтворена відмова.

| # | Несправність (fault) | Помилка (error) | Відмова (failure) | Тригер | Критичність |
|---|---|---|---|---|---|
| 1 | `async def` обробники викликають синхронний `Session.exec()` | Event loop заблоковано на час запиту до БД; інші запити стоять у черзі | Усі користувачі отримують великі затримки або тайм-аути; healthcheck Render не відповідає → рестарт сервісу | Повільна БД або кілька паралельних запитів | **Висока** |

### Підсумок класифікації

| Критичність | Знахідки |
|---|---|
| Висока | №1, №2, №3, №4, №6 |
| Середня | №5, №7, №8, №9a, №9b, №13 |
| Низька | №10, №11, №12, №14 |

**Спільний ланцюг для категорії E (§3.2).** Знахідки №1, №2, №3 і №5 мають ту саму природу: виклик, не
обмежений у часі. Вони підсилюють одна одну. Повільний запит (№5) без тайм-ауту (№2) або на блокуванні (№3)
тримає з'єднання з пулу, а через №1 ще й блокує event loop. Одна локальна несправність перетворюється на
відмову всього API. Тому на Етапі 3 першими варто виправити саме їх: спочатку тайм-аути, потім `def`
замість `async def`.
