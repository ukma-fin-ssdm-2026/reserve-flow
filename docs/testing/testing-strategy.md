## 1. Поточний статус тестування

## 3. Плани для інтеграційних, системних і приймальних тестів

- **Інтеграційні тести:** перевірка транзакційності при підтвердженні та скасуванні бронювань (US-004, US-006). Окрема увага приділяється нагадуванням (US-005, FR-014).
- **Системні тести (End-to-End API):** наскрізні сценарії пошуку та фільтрації приміщень за параметрами (US-007), а також повний цикл зміни статусу слотів постачальником (US-003).
- **Приймальні тести (Acceptance):** перевірка адміністративних сценаріїв через API (Swagger UI / сценарії `TestClient`): модерація нових кімнат (US-001), перегляд логів (US-002) та блокування користувачів (US-008).

### Етап 2 – Швидке планування

- **Обсяг:** Тестуємо основні бізнес-процеси бекенду `reserve-flow`: автентифікацію/RBAC, управління кімнатами й слотами, транзакційне бронювання та E2E-пошук. Свідомо НЕ тестуємо зовнішній SMTP-сервер у реальному середовищі (використовуємо моки) та UI/фронтенд (оскільки репозиторій містить лише REST API).
- **Критерії виходу:** Усі 197+ тестів успішно проходять у CI (PostgreSQL 16); покриття коду становить ≥ 98% загалом та ≥ 80% для кожного окремого файлу; відсутні вразливості (`bandit`, `pip-audit`) та критичні дефекти.
- **Ризики:** Найвищий ризик — колізії та race conditions при одночасному (конкурентному) бронюванні одного слота кількома користувачами (подвійне бронювання), а також можлива відмова авторизації при граничних значеннях JWT/паролів. Починаємо план з перевірки транзакційного блокування та безпеки.

## 4. Плани для тестування продуктивності, безпеки та property-based

- **Продуктивність (Performance):** PT-001 (PERF-001) — пошук ≤ 5 с при 10 одночасних користувачах; планується навантажувальний тест.
- **Надійність (Reliability):** RT-001 (REL-001, FR-006) уже реалізовано в `tests/test_booking_concurrency.py`: 10 паралельних бронювань одного слота → рівно одне успішне, перевіряє `SELECT … FOR UPDATE`; виконується в CI на PostgreSQL.
- **Безпека (Security):** тестування RBAC та валідації JWT-токенів на всіх захищених ендпоінтах (FR-002, SEC-001), зокрема межі строку дії токена (#257). Захист від Elevation of Privilege (спроба отримати права адміністратора → 403). Статичний аналіз коду — `bandit`, перевірка вразливостей залежностей — `pip-audit`.

- **Property-based (Hypothesis):** властивість хешування паролів перевіряється на згенерованих входах — див. «Бонуси».

## 5. Інтеграція в CI/CD

- **Job тестування (`tests`):** виконується на self-hosted runner з ОС Linux при кожному push та pull_request у гілку `main`.
- **Оточення:** тести запускаються проти реального сервісу БД (`postgres:16`) у тимчасовій базі `reserveflow_test`.
- **Артефакти:** підсумок покриття автоматично виводиться у `$GITHUB_STEP_SUMMARY` (Markdown). Детальний HTML-звіт завантажується як артефакт `htmlcov` із терміном зберігання 14 днів.
- **Ворота покриття:** крок «Coverage gate» у job `tests` — збірка падає, якщо хоч один файл має покриття < 80 %; загальний поріг — `fail_under = 80` у `pyproject.toml`. Деталі — у розділі «Бонуси».
- **Аудит залежностей:** `pip-audit` в окремому workflow `security.yml` — на кожен PR, push у `main` і щотижня.
- **Локально:** `pre-commit` (black, flake8, bandit, detect-secrets) перед кожним комітом.

## 6. Цілі якості та політика воріт якості (Quality Gates)

Погоджено з Анастасією Лавришин (Integration Lead).

Для злиття будь-якого PR у гілку `main` код має відповідати таким критеріям:

1. **Тестове покриття та Pass Rate:** покриття — не менше 80 % для кожного файлу (рядки + гілки), рішення T-03 у #248; перевіряється в CI (крок «Coverage gate», #260). Усі тести мають успішно проходити.
2. **Стиль коду (Zero Warnings Policy):** проходження `black` та `flake8` без помилок (job `lint`).
3. **Безпека:** відсутність вразливостей середнього та високого рівня за результатами `bandit -ll`; відсутність відомих вразливостей у залежностях (`pip-audit`).
4. **Синхронізація документації:** OpenAPI-специфікація (`openapi-generated.yaml`) має бути актуальною. Якщо код змінює контракти API, розробник оновлює її локальним скриптом, інакше CI job `api` відхилить PR.
5. **Архітектурна цілісність:** зміни логіки відповідають обмеженням модульного моноліту (заборона прямих крос-модульних запитів до чужих таблиць БД) — перевіряється на рецензії коду.

### Ворота покриття в CI (L6-13, #260)

- **Поріг:** **80 % для кожного файлу**, рядки + гілки (`branch = true`). Рішення T-03 у #248.
- **Як перевіряється:**
  - крок «Coverage gate» у job `tests` (`ci.yml`): `coverage json` → для кожного файлу `percent_covered`; якщо хоч один < 80 % — `::error` з назвою файлу, список у Summary прогону і червона збірка;
  - `fail_under = 80` у `pyproject.toml` — загальний поріг; його перевіряє `pytest --cov` і в CI, і локально;
  - `include_namespace_packages = true` — у `src/api` немає `__init__.py`, тож без цього файл, який жоден тест не імпортує, взагалі не потрапив би у звіт і пройшов би ворота.
- **Чому для кожного файлу, а не лише загальний:** перевірено на демо-гілці — новий модуль без жодного тесту (0 %) знижує загальне покриття лише з 98 % до 97 %, тож загальний поріг його пропускає, а поріг на файл — ні.
- **Чому 80 %, а не 90–100 %:**
  - зараз кожен файл ≥ 94 %, тож 80 % — запас для нових модулів, а не планка, яку «тягнемо» тестами заради відсотка;
  - 100 % не гарантує якості: межа «рівно 2 год» у правилі скасування була покрита рядком, але жоден тест її не перевіряв (челендж L6-07);
  - покриття рахуємо з гілками — 80 % гілок суворіше за 80 % рядків.
- **Що виключено і чому:** службові файли (`omit`) і блок `if __name__ == "__main__":` — див. розділ 2.

### Тести на основі властивостей — Hypothesis (L6-15, #262)

- **Інструмент:** бібліотека `hypothesis` (додана до `requirements-dev.txt`).
- **Модуль тестування:** `tests/test_properties.py` (функції безпеки `hash_password` та `verify_password`).
- **Перевірена властивість:** для будь-якого рядка (пароля) довжиною до 72 байтів хешування через `hash_password` із наступною перевіркою через `verify_password` завжди повертає `True`. Генератор `text(max_size=72)` рахує символи, тому додано фільтр `len(s.encode()) <= 72`: кирилиця займає 2 байти, і без фільтра bcrypt отримав би пароль понад ліміт (#295).
- **Обґрунтування:** алгоритм верифікації зобов'язаний гарантувати автентифікацію легітимного користувача незалежно від набору символів чи довжини секрету в межах ліміту bcrypt.
- **Оптимізація виконання:** `@settings(max_examples=10, deadline=None)` зберігає репрезентативність вибірки без надмірного сповільнення CI через ресурсомісткість хешування bcrypt.
- **Докази:** тест додано в PR #283; обмеження «байти, а не символи» — PR #295; тест виконується в CI в job `tests`.
- **Пояснює у відео:** Ромах (відео про внесок, `Labs/Lab06/video_Romakh.txt`, 2-й рядок).
