## L6-07. Межа правила 2 годин при скасуванні бронювання (FR-007)

| | |
|---|---|
| Гілка з помилкою (не мерджиться) | `debug/l6-07-break` |
| Регресійний тест у `main` | `tests/api/test_bookings_regression.py::test_cancel_deadline_boundary` (PR #277) |
| Місце помилки | `src/api/routes/bookings.py:251`, функція `update_booking` |
| Червоний прогін CI | Draft PR #<337> (закрито без злиття) — [Tests with coverage](<https://github.com/ukma-fin-ssdm-2026/reserve-flow/actions/runs/40700104716/job/122857277718?pr=337#logs>) |

### Симптом

З помилкою всі наявні тести (без регресійного) зелені:

```text
$ pytest tests -q --ignore=tests/api/test_bookings_regression.py
193 passed, 1 skipped
```

Проте клієнт, який скасовує бронювання рівно за 2 години до початку, отримує `409 CANCELLATION_TOO_LATE`,
хоча FR-007 дозволяє скасувати «не пізніше ніж за 2 години». Тест на межу падає:

```text
$ pytest tests/api/test_bookings_regression.py -q --tb=short
.F.                                                                      [100%]
______________ test_cancel_deadline_boundary[exactly-2h-allowed] _______________
tests/api/test_bookings_regression.py:38: in test_cancel_deadline_boundary
    assert response.status_code == expected_status
E   assert 409 == 200
E    +  where 409 = <Response [409 Conflict]>.status_code
FAILED tests/api/test_bookings_regression.py::test_cancel_deadline_boundary[exactly-2h-allowed]
1 failed, 2 passed
```

### Кроки налагодження

1. **Відтворення.** Тест із фіксованим «зараз» (`_now` підмінено): `now = slot.start_time - 2 год` → `PATCH` зі статусом `Cancelled` повертає 409, очікували 200.
2. **Ізоляція.** Параметризований тест має три випадки: `2h+1s` (200), `exactly-2h` (200), `2h-1s` (409). Падає лише середній, тож помилка не в ролі, статусі чи БД, а в порівнянні на самій межі. Наявні тести перевіряють 1 год і 3 год, тобто далеко від межі, тому її не бачили.
3. **Діагностика.** Умова відмови — `start_time - now < _CANCELLATION_DEADLINE`. Перевірка арифметики:

   ```text
   >>> from datetime import timedelta as t; d = t(hours=2)
   >>> d < d,  d <= d
   (False, True)
   ```

   Рівно 2 год із `<=` дає «запізно».
4. **Виправлення.** Повернули строге порівняння.
5. **Перезапуск.** Регресійний тест: `3 passed`; весь набір: `196 passed, 1 skipped`.

### Причина

`src/api/routes/bookings.py:251` (функція `update_booking`):

```diff
-        if slot and slot["start_time"] - _now() <= _CANCELLATION_DEADLINE:
+        if slot and slot["start_time"] - _now() < _CANCELLATION_DEADLINE:
```

Помилка off-by-one: `<=` вважає запізнілим і випадок «рівно 2 години».

### Виправлення

Зміна `<=` → `<`. Регресійний тест
[`test_cancel_deadline_boundary`](../../tests/api/test_bookings_regression.py) перевірено в обидва боки:
з помилкою він червоний, без неї зелений.

### Хронологія: перший червоний прогін був хибним

Перша версія регресійного тесту у CI упала з `assert 401 == 200` у всіх трьох випадках: тест використовував
токени заглушки (`mock-client-token`), а після переходу на JWT потрібен `auth("client")`. Червоний результат
був, але не через помилку в межі 2 год. Це помітили саме завдяки контрольним випадкам `2h+1s-allowed` і
`2h-1s-too-late`: коли червоніє весь параметризований тест, причина не в самій межі. Після виправлення
автентифікації червоніє лише `exactly-2h-allowed` (`assert 409 == 200`), тобто саме той збій.

### Урок

- Межі треба тестувати на самій межі, а не «десь поруч»: пара значень по обидва боки плюс саме граничне значення.
- Для порогових правил варто одразу писати параметризований тест `порогове значення ± мінімальний крок`.
- Червоний тест має падати з очікуваної причини: перед внесенням помилки переконайтеся, що тест зелений на чистому коді, і дивіться на текст падіння, а не лише на статус.
- Зелений набір не означає відсутності помилок; корисна проста мутація (змінити `<` на `<=`) і перевірка, чи хоч один тест червоніє.
