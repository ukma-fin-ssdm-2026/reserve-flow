# План тестування — Reserve Flow

Команда 3 · стан коду: `main` @ `1074d92` · вимоги — [`docs/requirements/rtm.md`](../requirements/rtm.md) · стратегія — [`docs/testing/testing-strategy.md`](../testing/testing-strategy.md)

**Обсяг.** Тестуємо бекенд API (FastAPI + PostgreSQL), який уже реалізовано: вхід і JWT, права доступу (RBAC), пошук слотів, керування слотами постачальником, створення / підтвердження / скасування бронювань, нагадування, конкурентність бронювання. Свідомо **не** тестуємо: інтерфейс і багатомовність (FR-004 — фронтенду немає), реєстрацію, модерацію кімнат і журнал дій для адміністратора (FR-001 у частині реєстрації, FR-011, FR-013 — кінцевих точок ще немає), реальну доставку email / push і повторні спроби (FR-015, REL-002 — немає сервісу доставки), фонову чергу нагадувань і час її реакції (FR-014 у частині відправки, PERF-002 — Notification Scheduler поки заглушка; тестуємо лише розрахунок часу нагадування, рядок 14), адмін-панель, крім блокування користувача (FR-012 — кінцевих точок адміністратора ще немає), HTTPS і шифрування at rest (SEC-001 — налаштування інфраструктури, не коду).

**Критерії виходу.** Тестування завершене, коли: усі тест-кейси плану зелені в CI (job `Tests with coverage` на PostgreSQL 16, RT-001 не пропущено); покриття ≥ 80 % для кожного файлу (рядки + гілки, ворота «Coverage gate» зі стратегії Лаб 6); немає відкритих дефектів з міткою `Blocking`; для кожного рядка плану є посилання на вимогу з `rtm.md`.

**Ризики (з них починається таблиця).** 0) Розрив між записом і читанням бронювань: `POST /bookings` пише в БД, а `GET` і `PATCH` працюють із заглушками `mocks.py` — створене бронювання не можна ні переглянути, ні скасувати (відомий дефект, `Blocking`). 1) Подвійне бронювання одного слота при одночасних запитах — пряма втрата довіри користувачів (REL-001). 2) Доступ до чужих даних: чуже бронювання, слот чужої кімнати, підроблений або прострочений токен (SEC-001, FR-002). 3) Помилки на межах часу: правило «за 2 год» при скасуванні, часовий пояс Києва та перехід на зимовий час (FR-007, FR-003). 4) Повільний пошук під навантаженням (PERF-001).

### Автоматична перевірка простежуваності «вимога ↔ тест» (L7-13, #326)

- **Як позначено тести:** на початку кожного тестового файлу — `pytestmark = pytest.mark.req("FR-007", ...)` з ID вимог з `docs/requirements/rtm.md`; службові тести без вимоги — `pytest.mark.no_req("причина")`. Мітки зареєстровано в `pyproject.toml` з `--strict-markers`.
- **Скрипт:** `scripts/check_traceability.py` читає `rtm.md` і мітки в `tests/` (без запуску тестів, через `ast`). Збірка падає, якщо: функціональна чи нефункціональна вимога не має жодного тесту; тест не має ні `req`, ні `no_req`; у мітці ID, якого немає в `rtm.md`.
- **Поза обсягом** (`[tool.traceability.out_of_scope]` у `pyproject.toml`, з причиною — як в «Обсязі» плану): FR-004, FR-011, FR-015, PERF-002, REL-002.
- **CI:** крок «Traceability (requirement <-> test)» у job `lint`; таблиця «вимога → кількість тестів → стан» — у Summary прогону.
- **Тести самого скрипта:** `tests/test_traceability.py` (6 тестів: усе гаразд; вимога без тесту; тест без вимоги; описка в ID; мітки класу й `no_req`; поза обсягом).
- **Що знайшов:** вимога PERF-001 (пошук ≤ 5 с, Лаб 2) не мала жодного тесту.

- **Зелений прогін (дірку закрито):** [PR #351, Traceability](https://github.com/ukma-fin-ssdm-2026/reserve-flow/actions/runs/40871267675/job/123438632752) — після тесту PT-001 (#350) з міткою `req("PERF-001")`: 15 з 15 вимог в обсязі мають тести.
