# Документація проєктування API

## Огляд архітектури

* **Базова адреса:** `http://localhost:3000/api/v1`
* **Стиль API:** REST
* **Автентифікація:** JWT Bearer-токени (наразі використовуються мок-токени для ролей)
* **Формат відповіді:** JSON (кодування UTF-8)
* **Стратегія версіонування:** версія в шляху URL (`/api/v1`), див. «Версіонування (D-01)»

## Модель ресурсів

### Ресурс Users
* **Кінцева точка:** `/auth`, `/admin/users` (у перспективі `/users`)
* **Опис:** керування користувачами системи (Клієнти, Постачальники, Адміністратори)
* **Атрибути:**
  * `id` (uuid): унікальний ідентифікатор
  * `full_name` (string): повне ім'я користувача
  * `email` (string): адреса електронної пошти
  * `role` (enum): `Client` | `Provider` | `Admin`
  * `is_blocked` (boolean): статус блокування акаунта
* **Зв'язки:**
  * має багато бронювань (як клієнт)
  * володіє/керує багатьма приміщеннями (як постачальник)

### Ресурс Rooms
* **Кінцева точка:** `/rooms`
* **Опис:** керування приміщеннями, доступними для бронювання
* **Атрибути:**
  * `id` (uuid): унікальний ідентифікатор
  * `provider_id` (uuid): відповідальний постачальник
  * `name_ua`, `name_en` (string): назва аудиторії українською та англійською
  * `building_ua`, `building_en` (enum): корпус українською та англійською (`Корпус 1` … `Корпус 10`, `КМЦ`, `Наукова бібліотека`, `Історико-музейний комплекс НаУКМА`)
  * `room_number` (string): номер аудиторії
  * `capacity` (integer ≥ 1): місткість (кількість осіб)
  * `has_projector` (boolean): наявність проєктора
  * `is_shelter` (boolean): чи є приміщення укриттям
  * `moderation_status` (enum): `Pending` | `Approved` | `Rejected`
* **Зв'язки:**
  * належить постачальнику
  * має багато слотів (slots)

### Ресурс Slots
* **Кінцева точка:** `/slots`
* **Опис:** керування доступними часовими проміжками приміщень
* **Атрибути:**
  * `id` (uuid): унікальний ідентифікатор
  * `room_id` (uuid): приміщення
  * `start_time`, `end_time` (datetime, ISO 8601 з часовою зоною, напр. `2026-10-15T14:00:00+03:00`): початок і кінець слота
  * `is_available` (boolean): чи доступний слот для нових бронювань
  * `closure_reason` (string, необов'язковий): причина закриття; обов'язкова, коли постачальник закриває слот
* **Фільтри пошуку `GET /slots`:** `room_id`, `date`, `start`, `end`, `capacity`, `has_projector`, `is_shelter`, `building`, а також `limit` / `offset`
* **Зв'язки:**
  * належить до приміщення (room)
  * має пов'язані бронювання (bookings)

### Ресурс Bookings
* **Кінцева точка:** `/bookings`
* **Опис:** керування бронюваннями слотів користувачами
* **Атрибути:**
  * `id` (uuid): унікальний ідентифікатор
  * `slot_id` (uuid): заброньований слот
  * `user_id` (uuid): клієнт, який створив бронювання
  * `status` (enum): `Pending` | `Confirmed` | `Rejected` | `Cancelled` — значення як у `Booking.status` у `data-model.md`; переходи — D-03 (`PATCH /bookings/{booking_id}`)
  * `purpose` (string): мета бронювання
  * `reason` (string): причина відхилення (обов'язкова для `Rejected`, FR-010) або скасування (за бажанням)
  * `created_at` (datetime): час створення
* **Зв'язки:**
  * належить користувачу (user)
  * закріплено за слотом (slot)

## Проєктні рішення

### Чому Code-First (Генерація OpenAPI)?
Ми обрали підхід Code-First за допомогою FastAPI та Pydantic, тому що:
* документація (Swagger UI/ReDoc) завжди гарантовано збігається з реалізацією;
* типи мови Python жорстко гарантують відповідність валідаційних схем;
* ітерації розробки швидші — зміни в коді одразу відображаються в контракті;
* YAML не треба підтримувати вручну (він автоматично експортується скриптом `export_openapi.py` для CI/CD).

### Іменування ресурсів та URL (D-02)
Ми уникаємо RPC-подібних екшенів та вкладеності:
* URL формуються виключно з іменників у множині (напр., `/slots`, `/bookings`).
* Жодних дієслів в URL — дія визначається HTTP-методом.
* Обмеження вкладеності: замість `/rooms/{id}/slots/{slot_id}` використовується плоска структура `GET /slots?room_id={id}`.

### Зміна стану ресурсів (D-03)
Замість створення окремих кінцевих точок для дій (наприклад, `POST /bookings/{id}/cancel`), ми використовуємо:
* єдину точку оновлення через метод `PATCH /bookings/{id}`;
* зміну стану шляхом передачі нового значення поля `status` (напр., `Cancelled`) із вбудованою валідацією бізнес-правил.

### Стратегія пагінації (D-05)
* Пагінація зі зсувом (`offset` та `limit`), бо вона найпростіша для нашого набору даних.
* Ліміт за замовчуванням: 20 елементів.
* Максимальний ліміт: 100 елементів.
* Відповідь загортається в об'єкт `Page[T]` та містить метадані: загальну кількість (`total`), поточні `limit`/`offset` і прапорець `has_more`.

### Обробка помилок (D-04)
Ми перевизначили стандартні помилки FastAPI для уніфікації:
* Єдина структура відповіді з помилкою (`ErrorResponse`).
* Машинозчитувані фіксовані коди помилок (`ErrorCode` enum, наприклад `SLOT_UNAVAILABLE`, `FORBIDDEN`).
* Зрозумілі людині повідомлення (`message`).
* Помилки валідації (`422`) містять деталі по кожному полю в масиві `details` (з полями `field` та `issue`).
* Кожна помилка містить `correlation_id` для легкого пошуку в логах сервера.

### Версіонування (D-01)
* Версія — у префіксі шляху: усі кінцеві точки починаються з `/api/v1`.
* У межах `v1` дозволені лише сумісні зміни: нові кінцеві точки, нові **необов'язкові** параметри та нові поля у відповідях.
* Несумісні зміни (видалення чи перейменування поля або кінцевої точки, новий обов'язковий параметр, зміна типу чи значень enum) — лише в новій версії `/api/v2`. Попередня версія підтримується, доки нею користуються клієнти.
* Застарілі елементи позначаються `deprecated=True` в анотаціях FastAPI, тож це видно у Swagger UI.
* Окремо від версії в шляху є версія документа OpenAPI (`info.version`, зараз `1.0.0`): вона змінюється з кожним релізом.
