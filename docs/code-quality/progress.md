# Прогрес розробки та стан прототипу

**Проєкт:** Reserve Flow (Team 3) · **Стан на 01.11.2026 (Проміжне оцінювання проєкту)**

Цей документ фіксує актуальний стан розробки прототипу Reserve Flow, описує наскрізно реалізовані бізнес-сценарії з реляційною базою даних PostgreSQL, перелічує компоненти беклогу (що ще не реалізовано), наводить інструкції із запуску та містить посилання на матрицю простежуваності вимог і план тестування.

---

## 1. Що реалізовано наскрізно з базою даних (компоненти HLD)

Станом на 1 листопада в системі реалізовано основний функціональний потік бронювання кімнат із повноцінною реляційною моделлю даних (PostgreSQL), транзакційною цілісністю, захищеною автентифікацією та автоматизованим CI/CD конвеєром.

Після реалізації та злиття PR #364 (правило заборони перетину слотів клієнта FR-016) та PR #370 (переведення кінцевих точок `GET` і `PATCH /api/v1/bookings` з моків на PostgreSQL) прототип підтримує наскрізний життєвий цикл без використання in-memory заглушок для основних операцій.

## 2. Що ще не реалізовано (Беклог / Out of Scope)

Відповідно до плану розробки та критеріїв середини семестру (поточна готовність: ~59%), наступні компоненти та функції винесені за межі поточного прототипу і заплановані на наступні ітерації:

1. **Реєстрація користувачів (FR-001 частково):**
   * Наразі користувачі попередньо створюються через `src/api/seed.py`. Публічної кінцевої точки самостійної реєстрації нових клієнтів та постачальників ще немає.
2. **Адміністративна панель (FR-012, US-008):**
   * Реалізовано перевірку заблокованого статусу користувача під час авторизації (`deps.py`), проте кінцеві точки повноцінного управління обліковими записами, глобального списку всіх бронювань та довідника кімнат адміністратора ще не імплементовані.
3. **Модерація приміщень адміністратором (FR-011, US-001):**
   * Кімнати завантажуються через seed або створюються постачальником без обов'язкового етапу розгляду та схвалення адміністратором.
4. **Перегляд системного журналу аудиту (FR-013, US-002):**
   * Логи аудиту автоматично фіксуються в таблиці `audit_logs` у транзакціях бази даних, проте API-маршрути для фільтрації та експорту журналу адміністратором поки відсутні.
5. **Фонова черга та відправка нагадувань (FR-014 частково, FR-015, REL-002):**
   * Модуль розрахунку часу сповіщень функціонує на рівні сервісу, але фоновий планувальник (scheduler), черга завдань та реальна інтеграція з поштовими шлюзами/Push-сервісами не підключені.
6. **Клієнтський веб-інтерфейс (Web SPA / FR-004):**
   * Фронтенд-додаток та багатомовність інтерфейсу перебувають на етапі проєктування. Наразі взаємодія із системою виконується через OpenAPI / Swagger UI (`/api-docs`) або MCP-сервер.

## 3. Зв'язок із вимогами та тестуванням

Поточний стан реалізації системи синхронізовано з основними документами якості та верифікації проєкту:

* **[Матриця простежуваності вимог (RTM)](../requirements/rtm.md):** містить актуальну карту відповідності кожної користувацької історії (`US-xxx`), функціональної (`FR-xxx`) та нефункціональної (`NFR-xxx`) вимоги до відповідних модулів коду та тестів.
* **[План тестування (Test Plan)](../validation/test-plan.md):** фіксує перелік тест-кейсів (`TP-00` – `TP-16`, `TR-01` – `TR-12`). З моменту усунення розриву між читанням і записом бронювань (PR #370) наскрізний сценарій життєвого циклу (рядок 0 плану) проходить успішно на рівні інтеграції з базою даних.
* **Стан покриття:** загальне покриття коду тестами перевищує 90% (локальний звіт у `htmlcov/index.html`), усі критичні шляхи валідації покриті модульними, інтеграційними та конкурентними тестами (`test_booking_concurrency.py`).

## 4. Як запустити прототип

Для розгортання та перевірки прототипу з чистого клону виконайте такі кроки:

### 4.1. Підготовка оточення та запуск PostgreSQL
```bash
# Клонування репозиторію
git clone https://github.com/ukma-fin-ssdm-2026/reserve-flow.git
cd reserve-flow

# Встановлення залежностей
pip install -r requirements.txt
pip install -r requirements-dev.txt

# Запуск контейнера PostgreSQL через Docker Compose
docker compose up -d db

# Ініціалізація та наповнення БД тестовими даними (Seed)
python src/api/seed.py
```

### 4.2. Запуск API сервера
```bash
uvicorn main:app --app-dir src/api --reload --port 3000
```
Після запуску інтерактивна документація Swagger UI доступна за адресою:
👉 **[http://localhost:3000/api-docs](http://localhost:3000/api-docs)**

Тестові облікові дані (пароль береться з `SEED_USER_PASSWORD` у `.env`, за замовчуванням `testpass123`):
* Клієнт: `client@ukma.edu.ua`
* Постачальник: `provider@ukma.edu.ua`
* Адміністратор: `admin@ukma.edu.ua`

### 4.3. Запуск перевірок якості та тестів
```bash
# Запуск повного набору тестів на SQLite / PostgreSQL
pytest tests/

# Перевірка покриття коду
pytest --cov --cov-report=term-missing --cov-report=html

# Перевірка стилю коду та форматування
black --check src/ tests/
flake8 src/ tests/

# Сканування на вразливості безпеки
bandit -c pyproject.toml -r src/ -ll
```

## 5. Стандарти розробки та відповідність якості

Перед злиттям до гілки `main` усі зміни проходять обов'язкові перевірки в CI:
* **Black & Flake8:** дотримання стилю PEP 8 та статичний аналіз відсутності невикористаних імпортів і помилок.
* **Bandit & detect-secrets:** перевірка відсутності захардкодzone-секретів, ключів і типових безпекових дефектів (детальніше: [Статичний аналіз коду та лінтери](static-analysis.md)).
* **CI Quality Gates:** проходження тестів на реальній PostgreSQL 16 у GitHub Actions із жорстким контролем покриття не нижче 80% на кожен файл.
