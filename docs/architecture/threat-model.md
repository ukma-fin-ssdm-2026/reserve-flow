# Модель загроз (STRIDE)

Цей документ описує результати моделювання загроз для системи онлайн-бронювання приміщень НаУКМА. Аналіз проведено за методологією STRIDE на основі діаграми розгортання з виділеними межами довіри (Trust Boundaries) та моделі даних (Data Model) з урахуванням чутливих атрибутів (`email`, `full_name`, `password_hash`, `role`).

## Межі довіри (Trust Boundaries)
* **TB1 - TB2**: Перетин між публічним Інтернетом (Web SPA) та внутрішньою мережею серверів (FastAPI) — найбільша поверхня атаки.
* **TB2 - TB3**: Перетин між сервером додатків та базою даних PostgreSQL.
* **TB2 - TB4**: Перетин між фоновим воркером та зовнішнім SMTP-шлюзом.

## Таблиця ідентифікованих ризиків та контрзаходів

| Межа / Компонент | Категорія STRIDE | Сценарій загрози | Оцінка | Контрзахід або свідоме прийняття ризику |
| :--- | :--- | :--- | :--- | :--- |
| **TB1 - TB2**<br>(Web SPA - FastAPI) | **Spoofing**| Зловмисник перехоплює мережевий трафік у публічній Wi-Fi мережі НаУКМА, щоб викрасти JWT-токен або пароль користувача і видати себе за нього. | Висока | **Контрзахід:** Використання виключно HTTPS для всіх з'єднань (вимога SEC-001). Зберігання паролів лише у вигляді bcrypt-хешів. |
| **TB1 - TB2**<br>(FastAPI API Layer) | **Elevation of Privilege** | Авторизований Клієнт намагається змінити свою роль (`role`) на `Admin` у тілі запиту або звертається напряму до прихованого адмінського ендпоінту `/api/admin/rooms`. | Висока | **Контрзахід:** Жорстка RBAC-авторизація на кожному ендпоінті (FR-002). Значення `role` береться виключно з підписаного payload JWT-токена, а не з тіла запиту клієнта. |
| **TB1 - TB2**<br>(Nginx → FastAPI, Booking APIRouter) | **Denial of Service** | Зловмисник масово надсилає тисячі POST-запитів на бронювання або на вхід (`/api/auth/login`), щоб вичерпати воркери Uvicorn і з'єднання з PostgreSQL та зробити сервіс недоступним для інших користувачів. | Середня | **Контрзахід:** обмеження частоти запитів у Nginx (`limit_req`, `limit_conn`) для `/api/auth/*` і `/api/bookings` з одного IP — Nginx уже розгортається як reverse proxy (HLD, розділи 5–6), тож це не потребує бюджету. Відповідь `429 Too Many Requests` при перевищенні ліміту.<br>**Примітка:** `SELECT FOR UPDATE` захищає цілісність (REL-001, жодного подвійного бронювання), а не доступність, тому не є контрзаходом від флуду.<br>**Прийняття ризику:** розподілену DDoS-атаку з багатьох IP свідомо не розглядаємо — для університетського проєкту без бюджету захист рівня Cloudflare WAF надлишковий. |
| **TB1 - TB2**<br>(Booking APIRouter) | **Tampering** | Зловмисник підміняє `booking_id` або `client_id` у POST/DELETE-запиті, намагаючись змінити або скасувати чуже бронювання (IDOR). | Середня | **Контрзахід:** Використання непередбачуваних `UUID` як первинних ключів. Додаткова обов'язкова перевірка в `Booking Engine Service`, що поточний авторизований користувач є власником цього бронювання. |
| **TB2 - TB3**<br>(PostgreSQL) | **Information Disclosure** | Інсайдер або зловмисник отримує несанкціонований доступ до файлів БД, викрадаючи персональні дані (`email`, `full_name`). | Висока | **Контрзахід:** Зашифрувати колонки з персональними даними за допомогою `pgcrypto`. |
| **TB2**<br>(AuditLog Service) | **Repudiation** | Адміністратор видаляє акаунт або постачальник закриває слот з чужою заявкою і заявляє, що «не робив цього, це баг». | Низька | **Контрзахід:** Будь-яка критична дія зі зміни стану фіксується у незалежній таблиці `AuditLog` із зазначенням виконавця (`user_id` або `actor_type = System` для дій планувальника), `action` та точної часової мітки (FR-013). Записи в логах імутабельні. |
| **TB2-TB4**<br>(Notification Scheduler - SMTP) | **Denial of Service** | Зовнішній SMTP-шлюз недоступний або вводить ліміти на відправку листів (R-001), що призводить до зависання черги сповіщень. | Середня | **Контрзахід:** Використання асинхронного клієнта з жорсткими таймаутами (5 с), не більше 3 повторних спроб з експоненційною затримкою (REL-002), фіксація збою в AuditLog (FR-015). |
