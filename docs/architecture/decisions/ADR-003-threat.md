# ADR 003: Механізм автентифікації та контролю доступу (JWT + RBAC)

**Статус:** Затверджено
**Дата:** 1 жовтня 2026
**Учасники:** Team 3

## Контекст

У процесі аналізу безпеки (threat-model.md) було ідентифіковано два високі ризики на межі довіри TB1 - TB2 (Web SPA - FastAPI):

    Spoofing: Перехоплення сесії або пароля користувача.

    Elevation of Privilege: Спроба клієнта отримати доступ до адмінських ендпоінтів або підмінити свою роль у запиті.

Враховуючи обраний в ADR-001 архітектурний стиль (SPA + REST API), потрібен безпечний механізм передачі авторизаційного стану (stateless), який захистить персональні дані та забезпечить строге розмежування доступу.

## Рішення

Ми обрали **JSON Web Tokens (JWT) для автентифікації у поєднанні з Role-Based Access Control (RBAC) на рівні FastAPI Dependencies для авторизації**.

    Зберігання паролів: Паролі ніколи не зберігаються у відкритому вигляді, а лише як незворотні хеші з використанням алгоритму bcrypt (вимога SEC-001).

    Автентифікація (JWT): Після валідації логіна/пароля сервер генерує Access-токен, у payload якого (підписаному секретним ключем сервера) зашиваються user_id та role.

    Авторизація (RBAC): Перевірка прав (FR-002) реалізується через механізм FastAPI Depends. Сервер довіряє лише значенню role, яке вилучається з підписаного JWT-токена, ігноруючи будь-які спроби клієнта передати іншу роль у тілі запиту.

## Альтернативи

    Stateful-сесії (Cookies + БД / Redis): Класичний підхід, де сервер зберігає ідентифікатор сесії. Відхилено, оскільки це вимагає розгортання додаткового компонента (Redis) або створює зайве навантаження на PostgreSQL при кожному API-запиті. Це порушує принцип простоти інфраструктури.

    Зовнішні Identity-провайдери (OAuth2 / Auth0 / Keycloak): Відхилено, оскільки вимоги проєкту (C-005) та обмеження часу (C-001) не передбачають складних сторонніх інтеграцій. До того ж, зберігання хешів локально задовольняє навчальні вимоги системи.

    HTTP Basic Auth: Відхилено через низький рівень безпеки (передача логіна/пароля в кожному запиті).

## Наслідки

- **Позитивні**:
        Stateless-природа: бекенду не потрібно звертатися до бази даних для автентифікації кожного запиту (роль і ID вже є в підписаному токені), що покращує продуктивність.

        Безпека: Захист від Elevation of Privilege (токен захищений криптографічним підписом, клієнт не може змінити свою роль).

        Сумісність: FastAPI має відмінну вбудовану підтримку OAuth2PasswordBearer та JWT.

- **Ризики та обмеження (Прийняття)**:
        JWT-токен неможливо "відкликати" до закінчення його терміну дії (актуально при блокуванні користувача за US-008).

        **Контрзахід**: Встановити короткий час життя токена (наприклад, 15-30 хвилин) та реалізувати примусову перевірку статусу is_blocked у базі даних для критичних ендпоінтів.

Використання ШІ: базові формулювання згенеровані ШІ Gemini відповідно до ідей команди, альтернативи запропоновані Gemini та відкинуті командою. Документ було перевірено,  відредаговано та затверджено учасниками команди.
