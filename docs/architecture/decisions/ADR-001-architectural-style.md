# ADR 001: Вибір архітектурного стилю

**Статус:** Затверджено
**Дата:** 30 вересня 2026 (оновлено 6 жовтня 2026: розширено розгляд альтернатив, список модулів узгоджено з HLD)
**Учасники:** Team 3
**Пов'язано з:** [high-level-design.md](../high-level-design.md), [component.puml](../uml/component.puml), [ADR-002](ADR-002-backend-framework.md)

## Контекст
Проєкт Reserve Flow потребує надійної архітектури для управління бронюванням приміщень. Ключові вимоги й обмеження, від яких залежить вибір стилю:

- **REL-001, FR-006** — жодного подвійного бронювання при одночасних запитах на один слот;
- **FR-002, SEC-001** — перевірка прав на кожен запит;
- **FR-014, FR-015, REL-002** — фонове надсилання нагадувань з повторними спробами;
- **C-001** — команда з 4 осіб, один семестр, без виділеного DevOps;
- **C-003** — реляційна база даних;
- **C-004** — збірка й тести в межах безкоштовного GitHub Actions.

## Розглянуті варіанти

| Варіант | Переваги | Недоліки для нашого проєкту | Висновок |
|---|---|---|---|
| **Мікросервіси** (окремі сервіси користувачів, приміщень, бронювань, сповіщень, кожен зі своєю БД) | Незалежне розгортання й масштабування; ізоляція збоїв | Бронювання й перевірка слота потрапляють у різні сервіси та БД, тож REL-001 потребує розподілених транзакцій (Saga / 2PC). 5+ контейнерів, окремий CI на сервіс, міжсервісна автентифікація — суперечить C-001 і C-004 | Відхилено |
| **Класичний моноліт без модулів** (усі маршрути працюють з усіма таблицями) | Найшвидший старт, одна транзакція для REL-001 | Логіка бронювання, прав і аудиту розмазується по маршрутах; 4 розробники постійно правлять ті самі файли | Відхилено |
| **Подієво-керована архітектура** (компоненти взаємодіють через брокер повідомлень) | Природна асинхронність для нагадувань (FR-014) і повторних спроб | Асинхронне бронювання створює вікно для подвійного резервування (REL-001); потрібен брокер (RabbitMQ / Kafka) і налагодження асинхронних потоків | Відхилено як основний стиль; асинхронність для нагадувань реалізуємо окремим фоновим процесом |
| **Модульний моноліт + SPA** | Одна БД і одна транзакція для REL-001; одна точка перевірки прав; модулі дозволяють працювати паралельно; 4 контейнери в одному `docker-compose` | Потрібна дисципліна, щоб модулі не перепліталися | **Обрано** |

## Рішення
Ми обрали **модульний моноліт (Modular Monolith) на бекенді з відокремленим Single Page Application (SPA) на фронтенді**.

Система складається з таких частин (детально — у [high-level-design.md](../high-level-design.md), розділ 4):

1. **Frontend (SPA):** вебклієнт на HTML + CSS + JS, який завантажується один раз і спілкується з сервером через REST API.
2. **Backend (модульний моноліт на FastAPI):** один процес `api`, поділений на шари та доменні модулі:
   - шар API — `Auth`, `Room`, `Booking`, `Admin` APIRouter;
   - доменні сервіси — `User & Auth Service`, `Room Management Service`, `Booking Engine Service`, `Audit Log Service`.
3. **Фоновий процес:** `Notification Scheduler` — окремий процес із тим самим кодом моделей, що надсилає нагадування (FR-014, FR-015).
4. **Database:** єдина реляційна база PostgreSQL. Кожен модуль змінює лише свої таблиці; читати чужі таблиці дозволено тільки для перевірок (наприклад, Room Management Service перевіряє активні бронювання слота, FR-009).

## Обґрунтування
- **Надійність (REL-001):** бронювання, блокування слота (`SELECT … FOR UPDATE`) і запис нагадування виконуються в одній транзакції однієї БД, без розподілених транзакцій.
- **Відповідність масштабу (C-001, C-004):** один код, один `docker-compose`, один CI. Мікросервіси для команди з 4 осіб на семестр надлишкові.
- **Організація коду:** модулі й шари не дають моноліту перетворитися на «спагеті-код» і дозволяють працювати над різними функціями паралельно.
- **Асинхронність там, де вона потрібна:** нагадування винесено в окремий процес, тож вони не гальмують запити користувачів і переживають збої SMTP (REL-002).
- **UX:** SPA забезпечує швидкий інтерфейс без перезавантаження сторінок.

## Наслідки
- **Позитивні:** низький поріг входу, проста інфраструктура (4 контейнери), чіткі межі між компонентами.
- **Ризики:** модулі можуть почати переплітатися. Заходи:
  - залежності між доменними сервісами лише в один бік (Booking Engine → Room Management, див. HLD, розділ 4.2.2);
  - перевірка на code review, що модуль не змінює чужі таблиці.
- **Шлях розвитку:** якщо навантаження зросте, найпростіше винести в окремий сервіс Notification Scheduler, бо він уже є окремим процесом.
