# ADR 002: Вибір бекенд-фреймворку — FastAPI

**Статус:** Затверджено
**Дата:** 1 жовтня 2026
**Учасники:** Team 3
**Пов'язано з:** [ADR-001](ADR-001-architectural-style.md), [high-level-design.md](../high-level-design.md), [component.puml](../uml/component.puml)

## Контекст

ADR-001 зафіксував стиль: модульний моноліт на бекенді та окремий SPA. Залишалось обрати технологічний стек бекенду.

Перша версія HLD описувала Java 17 / Spring Boot 3 + Angular. Водночас `Project-Description.md` (розділ 6) передбачає Python/FastAPI або Node.js/Express. Документи суперечили один одному, тож рішення треба було ухвалити явно.

Вимоги та обмеження, від яких залежить вибір:

- **REL-001, FR-006** — песимістичне блокування рядка (`SELECT … FOR UPDATE`) у транзакції, щоб не було подвійних бронювань.
- **FR-002, SEC-001** — перевірка JWT і ролі на кожному запиті.
- **FR-014, FR-015, PERF-002, REL-002** — фонове надсилання нагадувань кожні 30 с з повторними спробами.
- **C-001** — команда з 4 осіб, один семестр, без DevOps.
- **C-003** — реляційна БД (обрано PostgreSQL).
- **C-004** — збірка й тести в межах безкоштовного GitHub Actions.

## Розглянуті варіанти

| Критерій | Python / FastAPI | Java / Spring Boot 3 | Node.js / Express |
|---|---|---|---|
| Відповідність `Project-Description.md` | ✅ указано | ❌ не згадано | ✅ указано |
| `SELECT … FOR UPDATE` (REL-001) | ✅ SQLAlchemy `.with_for_update()` | ✅ JPA `PESSIMISTIC_WRITE` | ✅ через ORM (Prisma / Sequelize / Knex) |
| RBAC на кожен запит (FR-002) | ✅ залежності `Depends` у кожному роутері | ✅ Spring Security | ⚠️ middleware пишемо й підключаємо самі |
| Валідація запитів | ✅ Pydantic з коробки | ✅ Bean Validation | ⚠️ окрема бібліотека (zod / joi) |
| Документація API | ✅ OpenAPI і Swagger UI генеруються автоматично | ⚠️ потрібна бібліотека springdoc | ⚠️ описуємо вручну або окремою бібліотекою |
| Фонові задачі (FR-014) | ✅ APScheduler окремим процесом | ✅ `@Scheduled` | ✅ node-cron або BullMQ |
| Обсяг конфігурації для старту | Невеликий | Більший (Spring-контекст, анотації, збірка Maven / Gradle) | Невеликий |
| Досвід команди | ✅ 3 з 4 учасників розробили на FastAPI вебзастосунок «АІС Супермаркет» (курс «Бази даних та інформаційні системи») | ⚠️ досвід має 1 з 4 учасників | ❌ спільного проєкту на цьому стеку не було |

Усі три варіанти технічно виконують вимоги. Вирішальними стали досвід команди та відповідність уже затвердженим документам.

## Рішення

Бекенд реалізується на **Python 3.10+ / FastAPI** з таким набором бібліотек:

| Призначення | Бібліотека |
|---|---|
| ORM і доступ до даних | SQLModel / SQLAlchemy 2.0 |
| Автентифікація | PyJWT; хешування паролів — `pwdlib (bcrypt)` |
| Фонові задачі | APScheduler + SQLAlchemyJobStore, окремий процес |
| Сервер застосунку | Uvicorn (ASGI) |

Структура модульного моноліту з ADR-001 відображається так: кожен модуль = `APIRouter` (шар API) + доменний сервіс (шар бізнес-логіки).

## Обґрунтування

1. **Досвід команди (C-001).** Троє з чотирьох учасників уже розробили на FastAPI вебзастосунок «АІС Супермаркет» для курсу «Бази даних та інформаційні системи». Зі Spring Boot працював лише один учасник. За один семестр без DevOps це найважливіший чинник: з FastAPI троє починають без вивчення нового фреймворку, а зі Spring Boot таких було б лише один.
2. **Узгодженість документів.** FastAPI вже вказано в `Project-Description.md`, тож вибір прибирає суперечність між ним і HLD.
3. **REL-001.** `.with_for_update()` у SQLAlchemy дає те саме песимістичне блокування, що й JPA, без додаткових налаштувань.
4. **FR-002, SEC-001.** Механізм залежностей FastAPI (`Depends`) дозволяє оголосити перевірку токена й ролі один раз і підключати її до кожного роутера. Так ендпоінт без перевірки прав видно на рев'ю.
5. **Менше роботи для невеликої команди (C-001).** Валідація (Pydantic) і документація API (Swagger UI) не потребують окремого коду. Swagger UI також дає фронтенду готовий опис ендпоінтів.
6. **Фонові задачі.** APScheduler працює в окремому процесі з тим самим кодом моделей, що й API, без окремої інфраструктури черг.

## Наслідки

**Позитивні:**

- HLD, `component.puml`, `deployment.puml` і `Project-Description.md` описують один стек.
- Автоматичний Swagger UI можна використовувати як документацію інтерфейсів між SPA і бекендом.
- Тести пишуться на pytest; тест конкурентності RT-001 — паралельні запити через `httpx` / `asyncio`.

**Ризики та як їх знімаємо:**

| Ризик | Захід |
|---|---|
| Python не перевіряє типи під час компіляції, на відміну від Java | Анотації типів + `mypy` або `pyright` у CI |
| Асинхронні сесії SQLAlchemy легко використати неправильно (наприклад, блокування поза транзакцією) | Блокування і запис бронювання — лише всередині `async with session.begin()`; перевіряється тестом RT-001 |
| Фоновий процес і API — два окремі процеси з одного коду | Описано в HLD §6; запуск через `docker-compose` |
| Попередній проєкт команди використовував SQLite, а тут PostgreSQL. SQLite не підтримує `SELECT … FOR UPDATE`, тож механізм блокування для REL-001 для команди новий | Запускати тести на PostgreSQL (контейнер у CI), а не на SQLite; RT-001 — обов'язковий тест |
| Четвертий учасник не працював з FastAPI | Парне програмування або рев'ю його перших PR учасниками з досвідом |
