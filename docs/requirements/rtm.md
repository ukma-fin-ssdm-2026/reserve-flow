# Матриця простежуваності вимог (RTM)

Ланцюг: **бізнес-потреба** (`Project-Description.md`) → **користувацька історія** (`user-stories.md`) → **системна вимога FR / NFR** (`requirements.md`) → **код** (`src/api`) → **тести** (`tests/`, план — [`docs/validation/test-plan.md`](../validation/test-plan.md)).

Позначення тестів:
- `TP-NN` — рядок № NN тест-плану Лаб 7 (`test-plan.md`), тест уже є в `tests/` (крім TP-00, див. нижче);
- `TR-NN` — рядок таблиці переходів станів бронювання («Бонуси» тест-плану, `tests/api/test_booking_transitions.py`);
- у дужках «каталог» — потенційні тестові випадки Лаб 2 (розділ 2): `TC-###` — функціональний, `PT-###` — продуктивності, `ST-###` — безпеки, `RT-###` — надійності (конкурентності).

**Немає тесту** — вимога свідомо поза обсягом тестування; причину записано в «Обсязі» тест-плану і в `[tool.traceability.out_of_scope]` у `pyproject.toml` (скрипт `scripts/check_traceability.py` у CI перевіряє, що решта вимог має тест).

Статуси (стан на Лаб 7): `Перевірено` — тести плану зелені в CI; `Частково` — перевірено лише частину вимоги (яку — у дужках), решта не реалізована; `Відкритий дефект` — тест виявив дефект (рядок 0 плану або `xfail`); `Поза обсягом` — немає тесту (причина в дужках).

## 3. Зв'язок з архітектурою (Лабораторна 3)

Цей файл залишається реєстром вимог: історія → вимога → тест. Архітектурний зріз тих самих вимог — вимога → компонент → проєктне рішення → метод верифікації — ведеться в [`docs/architecture/traceability-matrix.md`](../architecture/traceability-matrix.md). Обидва файли використовують однакові ID вимог і тестів.

У Лабораторній 3 вимоги не змінювались, тому рядки матриці вище не оновлювались. Якщо вимога зміниться, оновлюються обидва файли. У Лабораторній 7 додано FR-016 — до обох файлів.
