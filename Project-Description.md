# Система бронювання

## 1. Призначення системи

Система призначена для бронювання приміщень у НаУКМА в онлайн-форматі. Вона вирішує проблему незручного та непрозорого процесу пошуку вільних кімнат — коли студентам і викладачам доводиться вручну уточнювати доступність приміщень, а кілька людей можуть одночасно намагатись зайняти один і той самий простір на один і той самий час. Система дозволяє зручно переглядати доступні кімнати та години, створювати й скасовувати бронювання, отримувати нагадування про заплановану подію, а також коректно обробляти одночасні запити на бронювання без конфліктів. Користувачами є студенти та викладачі (клієнти), відповідальні за приміщення (постачальники) та адміністрація університету.

## 2. Межі системи

**Входить в обсяг:**

-   Реєстрація/авторизація користувачів трьох ролей
-   Пошук доступних ресурсів (кімнат/слотів) за датою, часом, локацією, типом (напр. кількість місць, наявність проєктора, наявність укриття в будівлі/чи знаходиться приміщення в укритті)
-   Створення, перегляд, скасування бронювання
-   Обробка одночасних запитів на один ресурс (запобігання конфліктам)
-   Автоматичні нагадування (email/push) про наближення бронювання
-   Базова адміністративна панель (перегляд бронювань, блокування ресурсів)
-   Мультимовність інтерфейсу (українська, англійська)

**Свідомо поза обсягом (у цьому семестрі):**

-   Онлайн-оплата та інтеграція з платіжними системами
-   Мобільний застосунок (тільки веб)
-   Мультивалютність
-   Динамічне ціноутворення / система знижок
-   Інтеграція з зовнішніми календарями (Google Calendar тощо)
-   Чат або відеозв'язок між клієнтом і постачальником
-   Автоматична синхронізація з зовнішньою університетською документацією про приміщення та постачальників — усі зміни вносяться/погоджуються вручну адміністратором

## 3. Ролі і можливості користувачів

**Клієнт**

Реєстрація, пошук ресурсів, створення/перегляд/скасування власних бронювань, отримання нагадувань

**Постачальник**

Керування власними ресурсами: оновлювати статус слотів самостійно, додавати/редагувати кімнати за погодженням адміністратора, переглядати броні на свої ресурси, підтверджувати/відхилювати заявки

**Адміністратор**

Керування всіма користувачами та постачальниками, перегляд усіх бронювань, погодження запитів постачальників на додавання/редагування кімнати, блокування облікових записів, перегляд системних логів

## 4. Ключові функції

1.  **Реєстрація та автентифікація**  — створення акаунта з підтвердженням ролі (клієнт/постачальник/адміністратор).
2.  **Пошук доступності**  — фільтрація ресурсів за датою, часом, типом і локацією.
3.  **Створення бронювання**  — резервування конкретного слота з перевіркою на конфлікт.
4.  **Скасування бронювання**  — скасування клієнтом або постачальником з фіксацією причини й часу.
5.  **Система нагадувань**  — автоматичні сповіщення за N годин до бронювання.
6.  **Керування ресурсами постачальника**  — додавання/видалення/редагування кімнат (за погодженням адміністратора) чи слотів розкладу (самостійно).
7.  **Адміністративний огляд**  — панель для перегляду, модерації всіх бронювань і користувачів.
8.  **Ручне оновлення довідкової інформації**  — адміністратор вносить зміни щодо приміщень і постачальників за потреби, без автоматичної синхронізації із зовнішньою документацією університету.

## 5. Нефункціональні вимоги

1.  **Конкурентність:**  система повинна коректно обробляти щонайменше 10 одночасних запитів на бронювання одного й того ж ресурсу без подвійного резервування (перевірка транзакційним блокуванням або оптимістичним контролем версій).
2.  **Продуктивність:**  сторінка результатів пошуку доступності повинна відповідати не більше ніж за 5 с при 10 одночасних користувачах.
3.  **Безпека персональних даних:**  персональні дані клієнтів (ім'я, контакти, історія бронювань) повинні зберігатися у зашифрованому вигляді (at rest) і передаватися лише через HTTPS; доступ до чужих персональних даних заборонений на рівні API (перевірка авторизації на кожен запит).

## 6. Припущення та обмеження

-   **Стек:**  бекенд — Python/FastAPI, реляційна БД (PostgreSQL/SQLite/MySQL) для гарантій транзакційності при конкурентних бронюваннях.
-   **Зовнішні сервіси:**  email-нагадування через SMTP-сервіс (наприклад, SendGrid або локальний SMTP-сервер для демо); без реальної платіжної інтеграції.
-   **Наявні дані:**  тестові дані генеруються командою; реальних клієнтських даних не використовується.
-   **Обмеження команди:**  розробка одним семестром, команда 4 людини, без виділеного DevOps —  GitHub Actions використовується для CI/CD (лінтери, тести, збірка).
-   **Припущення:**  один ресурс (кімната/слот) може бути заброньований лише одним клієнтом на конкретний часовий інтервал; часові зони не враховуються (єдина часова зона для всієї системи).
