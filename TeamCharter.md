## 3. План комунікації
- **Основний канал:** чат в Microsoft Teams, де відбуваються переписка та дзвінки між учасниками команди
- **Розклад зустрічей:** Планові зустрічі в Microsoft Teams щосереди о 20:30 (EEST), позапланові узгоджуються за 24 години до зустрічі
- **Очікування щодо відповідей:** Кожен учасник зобов'язується відповідати на повідомлення протягом 24 годин

## 4. Співпраця та робочий процес
- **Стратегія гілкування:** Використовуємо спрощений GitHub Flow. Основна робоча гілка — `main`. Для кожної нової задачі створюється окрема гілка з префіксом типу задачі (наприклад, `bugfix/опис-помилки`)
- **Практики комітів:** Робимо дрібні та логічні коміти англійською мовою.  Формат: `тип: короткий опис`. Приклади типів: `feat` (новий функціонал), `fix` (виправлення багу), `docs` (документація), `refactor` (зміна коду без зміни логіки)
- **Правила огляду коду:** Жоден код не потрапляє в `main` без Pull request. Для злиття Pull request'ів потрібне схвалення мінімум від одного іншого учасника команди та успішне проходження автоматичних тестів CI
- **Робочий процес завдань:** Усі задачі ведуться на дошці GitHub Projects. Життєвий цикл задачі: `Todo` (відкрито) → `In Progress` (призначено на виконавця, йде робота) → `In Review` (створено Pull request) → `Done` (Pull request злито, задачу закрито)

## 5. Вирішення конфліктів
- **План вирішення конфліктів:** 
  1. Будь-які технічні розбіжності спочатку обговорюються асинхронно в коментарях до Issue або Pull request'ів
  2. Якщо згоди не досягнуто, ініціюється короткий командний дзвінок для пошуку компромісу
  3. Якщо конфлікт неможливо владнати всередині команди і він блокує подальшу роботу, проблема ескалюється до викладача

## 6. Доступність та робоче навантаження
- **Доступність учасників:** Кожен учасник команди присвячує роботі над проєктом орієнтовно 5-7 годин на тиждень (включно із командними зустрічами). Основний час для спільної синхронної роботи — вечірні години у будні дні (після 18:00) та вихідні
- **Балансування:** Якщо учасник розуміє, що не встигає виконати свої задачі через перевантаження або інші обставини, він зобов'язаний попередити команду щонайменше за 24 години до дедлайну. У такому разі незроблені задачі перерозподіляються між іншими учасниками через трекер завдань

## 7. Етична та професійна поведінка
- **Спільні принципи:** 
  - Усі учасники команди суворо дотримуються правил академічної доброчесності НаУКМА та базових принципів Кодексу етики ACM
  - Будь-який запозичений код чи текст (включно зі згенерованим ШІ) має бути належним чином перевірений та задекларований
  - Ми підтримуємо екологічну атмосферу в команді, ставимося до роботи колег із повагою, а критику висловлюємо конструктивно і лише щодо коду чи рішень, а не особистостей

## 8. Використання ШІ
- **Інструменти:** Claude, Gemini, ChatGPT, Github Copilot
- **Правила розкриття:** Лабораторні роботи міститимуть нотатку «Використання ШІ», яка чітко пояснюватиме, що було згенеровано та як це було перевірено. Команда відкрито повідомлятиме про використання ШІ на прямі запитання
- **Правило верифікації:** Згенерований код проходить ті самі механізми перевірки, що й написаний вручну (перегляд перед комітом, тести, взаємний огляд). Неперевірений згенерований код не потрапляє в основну гілку. Кожен учасник несе повну відповідальність за свій код, уникає неперевіреного вайбкодингу чи агентної інженерії та має бути здатним пояснити кожен свій рядок на захисті
