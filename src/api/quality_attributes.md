# Атрибути якості API

Цей документ визначає вимірювані цілі якості для API системи бронювання за категоріями стандарту ISO/IEC 25010, критерії їхнього невиконання, засоби перевірки, а також матрицю компромісів між ними.


## 1. Ефективність продуктивності

> **Зв'язок із NFR:** `PERF-001` (Ефективність продуктивності: сторінка результатів пошуку доступності повинна відповідати не більше ніж за 5 с при 10 одночасних користувачах).

* **Ціль:** 95-й перцентиль часу відповіді для ендпоінта пошуку слотів (`GET /api/v1/slots`) < 5 секунд при навантаженні у 10 одночасних активних користувачів.
* **Умова провалу:** p95 $\ge$ 5 секунд або наявність невдалих HTTP-запитів (> 0%) під час 5-хвилинного прогону сценарію тестування.
* **Реалізація:**
  * Пагінація відповідей списків (максимум 100 елементів на сторінку).
  * Індексація колонок дат і часових проміжків у базі даних.
  * Асинхронна обробка запитів на базі FastAPI/Uvicorn.
* **Вимірювання:** Сценарій навантажувального тестування в k6 або Apache JMeter (10 Virtual Users протягом 5 хвилин).

## 2. Надійність

> **Зв'язок із NFR:** `REL-001` (Надійність: 0 випадків подвійного резервування при обробці щонайменше 10 одночасних конкурентних запитів на один і той самий слот завдяки транзакційному блокуванню).

* **Ціль:** Рівно 0 випадків повторного/подвійного бронювання одного слота при одночасній обробці $\ge$ 10 паралельних запитів на бронювання (`POST /api/v1/bookings`).
* **Умова провалу:** Створення двох або більше записів бронювання для однакового `slot_id`, або повернення статусу `500 Internal Server Error` замість контрольованої бізнес-помилки `409 Conflict`.
* **Реалізація:**
  * Транзакційне блокування рядків у базі даних (`SELECT ... FOR UPDATE`).
  * Перевірка статусу слота перед збереженням із поверненням уніфікованого коду помилки `409 Conflict`.
* **Вимірювання:** Автоматизований стрес-тест на конкурентність (конкурентне надсилання 10 запитів на один і той самий `slot_id` за допомогою `pytest-asyncio` чи `httpx`).


## 3. Безпека

> **Зв'язок із NFR:** `SEC-001` (Безпека: 100% персональних даних клієнтів повинні зберігатися у зашифрованому вигляді і передаватися лише через HTTPS; 0% неавторизованих звернень до чужих даних на рівні API).

* **Ціль:** 0% неавторизованих звернень до захищених ресурсів (IDOR/BOLA); 100% передача трафіку через HTTPS; 0 вразливостей рівня `High` чи `Critical`.
* **Умова провалу:** Успішний доступ (статус `200`/`201`) до чужих бронювань чи дій без відповідного токена/ролі, доступність API незахищеним протоколом HTTP або наявність знахідок рівня High/Critical у безпековому звіті.
* **Реалізація:**
  * Обов'язкова автентифікація через `HTTPBearer` та перевірка ролей (`Role.CLIENT`, `Role.PROVIDER`) у FastAPI `Depends`.
  * Примусовий редирект на HTTPS і налаштування HSTS у продакшн-оточенні.
  * Шифрування чутливих полів у БД.
* **Вимірювання:** Набір безпекових автотестів на матрицю доступів (клієнт/провайдер/анонім) у `pytest`, а також автоматизоване сканування OWASP ZAP Baseline Scan.

## 4. Узгодженість

* **Ціль:** 100% відповідей з кодами помилок (4xx та 5xx) відповідають схемі `ErrorResponse` (код, повідомлення, кореляційний ID) без жодного повернення стандартного FastAPI-формату `{"detail": ...}`.
* **Умова провалу:** Поява хоча б однієї відповіді з помилкою у форматі `{"detail": ...}` або неперехопленого винятку зі стектрейсом.
* **Реалізація:**
  * Глобальні перехоплювачі винятків (`RequestValidationError`, `StarletteHTTPException`, `AppError`, `Exception`).
  * Наскрізна передача та генерація `correlation_id` для кожного запиту через middleware.
* **Вимірювання:** Інтеграційні тести API на невалідні вхідні дані, що перевіряють наявність ключів `error.code`, `error.message` та `error.correlation_id` у JSON-відповіді.

## 5. Документованість

* **Ціль:** 100% кінцевих точок API містять у специфікації OpenAPI описи, схеми вхідних/вихідних параметрів, а також релевантні приклади (examples) для кожного задекларованого HTTP-статусу.
* **Умова провалу:** Наявність кінцевої точки без опису параметрів, відсутність документації на будь-який із повертаних статусів помилок або наявність дубльованих нерелевантних прикладів відповідей у Swagger UI.
* **Реалізація:**
  * Використання генератора `error_responses()` з окремими схемами відповідей для кодів 401, 403, 404, 409, 422 та 500.
  * Використання `Field(..., description=..., examples=...)` у моделях Pydantic.
* **Вимірювання:** Автоматизована валідація специфікації `openapi.json` за допомогою лінтера Spectral під час збірки проєкту в CI/CD.

## 6. Сумісність 

* **Ціль:** 0 неоголошених руйнівних змін (breaking changes) у межах поточної версії `v1`.
* **Умова провалу:** Видалення полів із відповідей або додавання обов'язкових нових параметрів у запити без зміни префікса версії API.
* **Реалізація:**
  * Явне версіонування у префіксі шляхів: `/api/v1/`.
  * Використання прапорця `deprecated=True` замість видалення полів чи кінцевих точок.
* **Вимірювання:** Перевірка зворотної сумісності за допомогою інструментів аналізу різниці специфікацій (наприклад, `openapi-diff`) у процесі Pull Request перевірок.


## Матриця компромісів

| Атрибут | Компроміс | Вплив на систему | Заходи пом'якшення |
| :--- | :--- | :--- | :--- |
| **Безпека** *(валідація та перевірка ролей)* | Додаткові обчислення та декодування токенів на кожен запит | **Продуктивність:** незначне збільшення затримки обробки запиту (overhead ~5–15 мс) | Кешування публічних ключів/перевірок; оптимізація моделей валідації Pydantic |
| **Надійність** *(транзакційне блокування)* | Блокування рядків у БД (`FOR UPDATE`) під час оформлення бронювання | **Продуктивність:** потенційне утворення черги запитів на популярний слот | Встановлення жорсткого таймауту на блокування транзакції (`lock_timeout`), швидке завершення транзакції |
| **Надійність** *(логування інцидентів)* | Необхідність фіксації повного контексту помилки для відладки | **Безпека:** ризик витоку персональних даних клієнта або паролів у логи | Маскування чутливих даних у логах; клієнту надається лише `correlation_id` без внутрішніх деталей системи |
| **Узгодженість** *(єдиний ErrorResponse)* | Заміна вбудованих обробників FastAPI на власні фабрики помилок | **Трудомісткість розробки:** вища складність підтримки коду на старті | Створення універсальних хелперів та декораторів (`AppError`, `error_responses`) у спільному модулі `errors.py` |
